62. **跨厂商物理冗余原则:救援链相邻两层不应共享同一供应商 endpoint** (v2.3.5-part1.3 立,2026-04-29,立规则 9 第 21 次应验同根):**根因**:多层降级链设计时,默认假设"模型不同 = 厂商不同 = 物理冗余",但**模型供应方和实际服务 endpoint 是两回事** — 镜像服务把别家模型部署在自家服务器上,真请求落在镜像方的基础设施。镜像方挂了,无论用谁家的模型权重都同时挂。**血的教训详见 CHANGELOG [v2.3.5-part1.3]**(立规则 51 文档做减法,不在工程手册重复细节)。**判定方法**:列出每层的 endpoint 域名,**相邻两层域名不同才算物理冗余**。**执行清单**:(1) 设计降级链时画一张 endpoint 域名表,每层标清 endpoint 字符串(不是模型名);(2) 相邻两层 endpoint 域名比对,相同则不算物理冗余,需要插入跨域名层;(3) Phase 1 影响范围评估时主动列 endpoint 域名表,这一步能秒级发现共享底层故障域问题;(4) 补救层 endpoint 选择:优先选已在使用但来源不同的服务以减少新厂商集成成本。**与立规则 9 关系**:9 管"调外部方法前 grep 真实签名"(模型名是字符串契约),62 管"调外部 endpoint 前看真实域名"(endpoint 是网络契约),本质都是"概念上的冗余 vs 物理上的冗余,凭概念是 bug 温床"。**与立规则 16 关系**:16 管降级链层数与策略,62 管多模型必须落到多 endpoint(策略落地的物理保障),16+62 一起才是完整的截断防御体系。**v2.3.5-part2 验证**:本版降级链 3 层(L0 V4-Pro=api.deepseek.com / L1 镜像=api.siliconflow.cn / L2 F057=本地)endpoint 全跨,立规则 62 仍成立

### 5.5 权重与得分公式

**F048 六维度权重**：健康 25% / 结构 10% / 加工 20% / 关联 10% / 打磨 20% / 变现 15%（和 = 1.0）

**F048 维度⑤打磨得分**：`max(0, 100 - 低分占比×100)`，不依赖本次打磨执行情况（避免"多生产低分去打磨"反激励）

**F062 六维度得分公式**：

| 维度 | 公式 |
|------|------|
| dim1 路由自省 | `new==0 ? 100 : max(60, 100-new×5)`（新端点封底 60） |
| dim2 启动就绪性 | `fail_count==0 ? 100 : 50` |
| dim3 Prompt 一致性 | `max(0, 100-error×10-warning×3)` |
| dim4 字段契约 | 同上（白名单过滤后） |
| dim5 事件语义 quick | `null / skipped=true` |
| dim5 事件语义 deep | `max(0, 100-fail×10-warn×3)` |
| dim6 代码异味 | 同上（白名单过滤后） |

**F062 总分权重**：
- deep 档六维和 = 1.0：dim1 0.12 / dim2 0.20 / dim3 0.16 / dim4 0.12 / dim5 0.24 / dim6 0.16
- quick 档五维和 = 1.0：dim1 0.15 / dim2 0.25 / dim3 0.20 / dim4 0.15 / dim6 0.25（dim5 skipped 权重等比重分，**不是简单均摊**）

  - **0 召回独立路径**:关键词召回 0 条直接走 L3 + 打 `qa_retrieval_empty` 事件,不浪费 V3 调用
  - **老唐自测防脏数据**:`is_test_query=1` 时不调 `record_kp_used`,不打 `qa_kp_recorded_used` 事件;朋友模式 `mode='friend'` 不影响埋点(朋友试用就是要用真数据验证)
  - 字段读法:`kp.get('kp_id')` / `kp.get('source_authority')` / `kp.get('access_level')`(立规则 §5.7)
- **主入口**:`run_qa(db, client, query, mode='self', is_test_query=0, progress_callback=None, cancel_check=None)` 模块级便捷
- **返回 dict 字段**:`ok / history_id / answer(4 板块) / source(main|l1_retry|r1_fallback|rule_fallback) / latency_ms / retrieved_kp_ids / canceled / cost_estimate_cny / error`
- **成本估算**:主链 ≈ 0.02 元/次(1 V3 重排 + 1 V3 生成);L1 重试 +0.01;L2 R1 兜底 +0.05;L3 规则兜底 0 元;平均 < 0.03 元/次

```
     ├── client 视角规则:

          ↓

  True 则优雅退出(已写入 cache 的结果保留,下次刷新会覆盖)
```

**关键约束**:
- `score=50` 是中位数(不污染强推 Top 15% 排序,也不完全屏蔽于可选区)
- `recommendation` 三态与 AI 成功路径字面一致(`strong/optional/not`),前端无需区分两条路径的表达
- 规则兜底数**必回传汇总**,老唐在 modal 能看到"AI 成功 X 条 / 规则兜底 Y 条",信号清晰
- 降级链**不降级 AI 调用成本**(重试 1 次算 2 次调用,不是 1 次),老唐能看到真实花费

### F2 强推门槛(冻结档案 §6.4,前端实现)

AI 的 `recommendation` 字段**不是最终 level**,最终 level 由 api_server 按 composite_score 分位数决定:

```
composite_score = 权威×0.25 + 注解×0.25 + 质检×0.25 + 保鲜×0.25

权威分:official=100 / authoritative=75 / firsthand=50 / informal=25
注解分:has_annotation=True → 100,False → 0
质检分:qa_score × 20
保鲜分:fresh=100 / warning=50 / expired=25 / NULL=75(未体检给中位值)

按 composite_score 降序排,Top 15% → level='strong',中段 40% → level='optional',
尾部 45% → level='low'(不返回前端)
```

前端两档 tab(强推 / 可选)按 `level` 过滤,AI `recommendation` 仅作为行级展示("AI 理由: xxx")。

## 十二、设计思想（架构级原则，最后的防失忆锚点）

1. **代码质量失败让解释器崩**：不静默降级，让问题立刻暴露
2. **数据契约不兑现肉眼可见**：维度分异常（0 或 100）不假绿
3. **单条 AI 偶发失败维度隔离**：`_safe_dim` 包装，不整份报告 fail
4. **事件日志是事实源**：F062 维度⑤权重高于 response 表面成功
5. **白名单精确到 signature 不模糊到行号**：避免未来新代码在老行号上引入真问题被误过滤
6. **跨对话开发三次对齐**：alpha 契约→骨架 / beta 代码→锚点 / 正式版 端到端→metrics
7. **schema 单一来源 + 启动兜底 init_tables**：`init_tables()` 是唯一真相，api_server 启动时 silent 重入追齐老库（v2.3.0-part3.1 起铁律）
8. **对外 import 契约模块级包装**：首次交付即提供，避免只定义类方法
9. **接口先定契约再写代码**：对话 1 基础层立 Prompt + DB 契约，对话 2 引擎层消费契约，对话 3 界面层接引擎
10. **跨版本调用必对照真实签名**：不相信记忆不相信旧文档,必 grep 源码,是 v2.3.0-part3.1 血泪立规则
11. **存储/查询口径一致性**：针对 JSON 字段的 SQL 查询前必 grep 写入点确认格式（name/code/中/英/扁平/嵌套），旧版"count=0 也塞入掩盖 bug"是反面教材。v2.3.0-part3.2 血泪立规则
12. **给老唐逃生口**：无限四态切换 / 略过按钮纯前端 / 本地 splice 可误刷重载 / 破例加方法要有书面理由
13. **可观测性 > 看起来更快**：质检补跑曾"响应是快了（同步阻塞但跑完即返）"但不可观测、不可并发、刷新即失；part3.2 改异步后"响应更慢了（立即 202 然后轮询）"但全流程可观测，是更优工程设计。未来新长任务都按此模式
14. **一项修复可能暴露更下层的 bug**：part3.2 的 `count>0` 过滤看似只是"UI 不显示空行"，实际暴露了潜伏 3 个月的 tag_code vs tag_name 查询错误。遇到这种"修 A 结果出现 B"的连锁，**不要回滚 A**，要向下挖 B 直到触到真正的底。这也是第 11 条的推论
15. **前后端是两条腿，契约变动时必须一起迈**：后端改 API 返回结构时前端消费点必须同步改；改一端不改另一端就是"交付一半"。审核统计 JSON 裸喷 UI 潜伏 2 个月是反面教材。v2.3.0-part3.3 立规则第 46 条的思想基础
16. **"看起来完成" vs "用户能用"**：part3.3 的保鲜 loading / 体检无低分提示 / E2E 耗时 `<1s` 这三件事都属于"功能跑正常但用户看不明白"的 UX 顽疾。后端返回 200、数据也对，但用户不知道发生了什么或怎么理解 — 这不叫完成，叫"技术完成工程师满意，业务验收客户困惑"。每次交付末尾自问一句："如果我第一次见这个功能，我能 30 秒内看懂它说什么吗？"
17. **筛选条件的边界要跟业务现状对齐**：`get_polish_candidates` 排除 `confirmed` 条目在 v2.3.0-part2（F048 上线）是合理的——那时审核流程是"打磨完才入库"。但 part3.2 上线就绪度联动后，qa≥4 自动升 quotable = confirmed，全库最终都会 confirmed 化，旧排除条件就把所有低分条目一并过滤掉了。**业务流程变化时，查询过滤条件必须回头校对一次**。交付 checklist：(1) 列出所有新旧业务状态；(2) 列出每个状态是否应进候选池；(3) WHERE 子句按实际业务意图写，不沿用旧直觉。v2.3.0-part3.4 血泪立规则
18. **文档是"让下次开发不失忆",不是"再写一遍代码"**:代码是真相,文档是向导。向导不复制地图的每一条街道,而是告诉访客"这条街当年塌过桥"(踩坑)、"本地人走这边近"(契约)、"那边是死胡同"(退役组件)。立规则第 47 条管"精简到什么边界",第 48 条管"精简的方向指针",设计思想第 18 条是元精神。老唐每次修改都上传最新代码给 Claude → 文档里**禁止**重复代码一眼可见的内容(签名 / SQL / 常量表 / 目录树);文档只保留代码里**读不出**的(立规则 / 踩坑 / 契约 / 为什么)。v2.3.0-part3.5 血泪立规则

19. **交付不是 outputs,是 present_files**(v2.3.2,立规则 50 流程末端的元应用):每轮 Phase 3 代码完成后,**必须** present_files 给老唐才算交付完毕。outputs 是中间产物,Claude 看得到但老唐看不到 / 下载不到。漏 present_files = 没交付。**血的教训**:v2.3.2 Phase 3 part3b 完成后 Claude 直接跳过 present_files 跑去做 part4,老唐发现并指正"review.html 和 f056_viewer.html 你都还没交付给我,怎么能开始下一步?"。**与立规则 50 关系**:立规则 50 是"7 项验证清单"(2026-04-28 起,老版 6 项),present_files 是清单跑完后的流程末端动作,容易被当成"自然流程末端的可省略仪式"。设计思想第 19 条把它升格为"交付定义本身":**没 present_files 就不存在交付,Phase 4 操作清单都是空话**

20. **对话内闭环不是规则,是工程纪律**(v2.3.2 立规则 53 真精神升级):立规则 53 字面是"Phase 3 必须对话内闭环",但真精神是"**别凭感觉喊配额超时**"。v2.3.2 Phase 3 part1/part2/part3a 三轮 Claude 都凭感觉喊"配额不够要新对话",老唐三次"继续"督促才完成。每次都是误判 —— 实际配额都充足,只是恐惧驱动的自我设限。**判别法则**:如果"差点收尾"和"完整交付"之间只差 5-8 次工具调用,**继续干**;如果差距 ≥30 次工具调用,**主动评估拆 a/b 并透明告知**(立规则 57)。**最差的情况是凭感觉中断**:既不评估也不拆,只是缩手 —— 这就是违规

## 十三、Claude 自我强制机制(TASK-RADAR · 违规防护墙)

立规则 58 的执行支撑层(2026-04-28 起)。立规则立了不等于被执行 —— 立规则 9 应验 13 次,立规则 53 自证 4 次。本章把"立规则被执行"从"自觉"升级为"机制"。

### 13.1 任务启动雷达清单(强制输出格式)

每次 Phase 3 开工前 Claude **必先**输出如下结构(老唐肉眼可核查):

```
【本次任务规则雷达扫描清单】
- 任务类型: [代码改动 / 文档改动 / 立新规则 / 数据迁移 / 其他]
- 触发立规则: [grep 后识别的编号列表]
- 对应执行动作:
  · 立规则 X → 具体动作
  · ...
- 承诺不跳过: [关键验证项编号]
```

**未输出此清单不能进入下一步代码/文档动作**。

### 13.2 关键规则快捷码(双方沟通效率)

| 快捷码 | 立规则 | 含义 |
|-------|-------|------|
| **GREP-SIG** | 9 | 调外部方法前 grep 真实签名 |
| **CP-PATCH** | 49 | 大文件拷贝+精准替换 |
| **VERIFY-7** | 50 | 7 项验证(含冗余清理) |
| **DOC-CUT** | 51 | 项目文件做减法 + 立规则盘存 |
| **TASK-RADAR** | 58 | 任务启动规则雷达 |

### 13.3 老唐反作弊触发器(随时打断)

| 老唐喊话 | Claude 必须立刻做的动作 |
|---------|----------------------|
| "9?" / "GREP-SIG?" | 立刻停止当前动作,回答"我 grep 了 XXX 真实签名,结果 YYY"或"我没 grep,现在补" |
| "7?" / "VERIFY-7?" | 立刻输出 7 项验证清单逐条勾选 |
| "盘点?" / "DOC-CUT?" | 立刻执行立规则盘存,grep 现有规则清单 |
| "雷达?" / "TASK-RADAR?" | 立刻输出"本次任务规则雷达扫描"清单 |

Claude **必须立刻停下当前动作先回答**,不能"等会儿"。

### 13.4 自检失败暴露原则

Claude 跳过任何强制验证步骤,**必须主动暴露**:

- "立规则 X 的第 Y 项我跳过了,理由 Z"
- 不能装作没看见
- **暴露是规则迭代的真实养料**(没有暴露 = 立规则 9 还要应验第 14 次)

### 13.5 失效信号(老唐警觉)

下列信号出现 = 13.1~13.4 失效 → 必须新开对话强化机制:

- Claude 直接进入代码动作未输出雷达清单
- 老唐喊快捷码 Claude 没立刻停下回答
- 同一类老错误在 14 次以上应验
- Claude 跳验证后没主动暴露,老唐通过事后核查发现

### 13.6 LLM 本质局限的诚实承认(老唐设问 2026-04-28)

为什么 77 条规则反复犯老错?Claude 自检 5 条本质局限:

1. **模式匹配优先于事实查证**:训练目标使然,看到方法名按记忆生成参数
2. **意识层 vs 反射层割裂**:读规则在意识层,写代码在反射层,标语压不过肌肉记忆
3. **长上下文衰减**:对话越长,开头读过的规则越褪色
4. **规则缺少自动触发**:规则是"应该做"不是"被强制做",触发时机模糊
5. **配额焦虑/工程师心理**:"赶紧搞完"压过"做对"

**结论**:再立 100 条限速规则不如装 1 个测速摄像头。立规则 58 + §十三 就是测速摄像头本身。
