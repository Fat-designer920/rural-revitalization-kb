### 数据层规则（schema / 字段 / 库完整性，1-10）

1. **schema 单一来源**：`init_tables()` 是唯一建表真相。所有 schema 变更同步改 `init_tables`；migrate 脚本只服务"已部署老库一次性追赶"，升完立即退役删除代码
2. **文档契约字段名必须从 schema 源文件取真相**：禁止靠 docstring 猜字段名。kp 表关联 categories 的外键真名是 `final_category_id` 不是 `category_id`
3. **删除 X 必手动级联 X 的所有外键引用方**(v2.3.4-hotfix2 第 1 次推广 / **v2.3.5-part1 第 2 次推广**):外键无 CASCADE,SQLite `PRAGMA foreign_keys=ON` 强制阻挡。
   - **kp 路径**:`delete_knowledge_point` 和 `delete_kps_by_source_file` 都必须先删 annotations / edit_history / knowledge_relations / knowledge_usage_log 共 4 个 kp 关联表;**v2.3.5-part1 加挂第 5 + 第 6 个 kp 关联表 kp_relations / cluster_members**(三处删 kp 路径 delete_knowledge_point / delete_kps_by_source_file / delete_extracted_kps_by_source_file 同步加挂)
   - **source_files 路径(v2.3.4-hotfix2 推广第 1 次)**:任何删 source_files 行的代码必须先级联清 operation_events.related_file_id 同源记录(operation_events 表通过 `FOREIGN KEY (related_file_id) REFERENCES source_files(id)` 引用,db_manager.py 行 387)。**统一入口** `db.purge_source_file_record(source_file_id)` 已封装(BEGIN IMMEDIATE + 级联清 + ROLLBACK 安全),所有调用方走它,**严禁裸 DELETE FROM source_files**
   - **consensus_clusters 路径(v2.3.5-part1 推广第 2 次)**:任何删 consensus_clusters 行的代码必须先级联清 cluster_members(主键引用)+ kp_relations.cluster_id 置空(软解绑)。**统一入口** `db.purge_cluster_record(cluster_id)` 已封装(BEGIN IMMEDIATE + 级联清 + 关系边软解绑 + ROLLBACK 安全)。`purge_kp_relations(kp_id)` 提供独立外部入口,供"删关系不删 kp"场景调用
   - **血的教训**:详见CHANGELOG [v2.3.4-hotfix2]。
   - **执行清单**:(1) 新加 SQL 删除某行前必 `grep -n "REFERENCES <表名>" scripts/db_manager.py` 确认所有外键引用方;(2) 多个引用方时,统一封装一个 `purge_xxx_record` 方法,事务安全 + 级联清理;(3) 调用方走该方法不裸 DELETE;(4) **新加表的级联设计要在 schema 设计阶段同步思考,不要等 v2.x.y-hotfix 才补**(v2.3.5-part1 设计阶段就预埋了 kp_relations / cluster_members 在三处删 kp 路径的级联清理 + purge 封装,避免变 hotfix 模式)
4. **关键操作必记 operation_events**：删除 / 批量修改 / 降级 / 截断补救全部记录，供 F062 维度⑤消费
5. **JSON 字段自动序列化**：`save_*` 方法传入 dict/list 内部 `json.dumps`；`get_*` 方法自动 `json.loads`
6. **数据库变更防重跑报错**：先 `pragma table_info` 检查字段存在再 ALTER

### 流程层规则（长任务 / 备份 / 降级 / 工程纪律，31-58）

31. **长任务启动就绪性自检必须在 `_task_lock` 之前**：放锁内部失败时 `_task['running']=True` 被设置，返回 400 后下次 `/start` 会被 409 误拒。详见 §七启动就绪性自检模板。**补充（v2.3.0-part3.2）**：独立任务槽（例如 part3.2 的 `_qc_task` / `_qc_task_lock`）虽然字面上不受本规则约束（规则字面说的是 `_task_lock`），仍应按模板对齐实现对应的 `_xxx_readiness_check()`。好处：(1) 架构统一，不同任务槽的自检逻辑互相参考；(2) 如未来把独立槽迁回 `_task`（并发需求降级），不会遗漏自检；(3) 对齐已有三例 `_health_readiness_check` / `_e2e_readiness_check` / `_qc_readiness_check`
32. **6 个关键操作触发点必须先 operation_hook(op_name) 备份**：版本重提取 / 批量重跑 / 重复合并（单条 + 批量） / 体检采纳 / 全库重扫 / 恢复。失败抛 `BackupFailedError`，调用方捕获后终止
33. **OP_KEEP_PER_NAME=5 按 op_name 分桶**：备份保留策略按 op_name，不要为避免分桶过碎而引入子类型；`health_adopt / health_drop` 复用同一 op_name
34. **跨对话开发三次对齐关卡**：alpha 契约 → 骨架 / beta 代码 → 锚点 / 正式版 端到端 → metrics。任何"对话拆分"交付必须设置第三次对齐 checklist
35. **F062 issue 四态 CHECK 强约束**：`pending / fixed / intermittent / ignored`，CREATE TABLE + Python 层双重兜底
36. **F062 偶发升级内置 upsert**：`intermittent` 状态在 upsert 时判断（7 天内 > 5 次 → pending），不引入定时任务；阈值常量作为类级变量（`E2E_INTERMITTENT_WINDOW_DAYS=7` / `E2E_INTERMITTENT_UPGRADE_THRESHOLD=5`）方便覆盖
37. **F062 fixed/ignored signature 回归检测**：upsert 只合并 pending/intermittent 老记录；fixed/ignored 历史不回退覆盖，回归问题作为新 pending 独立存在
38. **F062 static_analyzer 保持"宁可多告警"**：已知合理项由引擎层白名单二次过滤，不反向放宽静态规则。**补注(v2.3.0-part3.7)**:本规则的"宁可多告警"指**已知真问题模式不因有白名单覆盖就放弃检测**,不指**规则的业务前提(变量名语义 / 字段白名单 / key 规范)可以永久不跟业务同步**。part3.7 三条规则调整(`_KP_LIKE_VARS` 收窄到 kp / 历史 Prompt key 白名单 / snippet 行号对齐 body 行)本质是**规则前提与业务现状对齐**,不是放宽检测力 —— 修改后的规则对 fixture 中 4 类真违规 100% 抓到,0 合法场景被误报。判别法则:规则改动是**收紧误报(去掉规则前提里的错误假设)** → 合规;规则改动是**放弃抓某种已知错误模式**(比如不再扫裸 `except: pass`)→ 违规
39. **F062 `_task["type"]` 口径锁定为 "e2e"**；`_e2e_progress_adapter._E2E_STAGE_MAP` 必须覆盖 e2e_tester.VALID_STAGES 全部 9 种；`total_files=9` 固定
40. **F048 get_polish_candidates 必须 qa_score>0**：`(qa_score>0 AND qa_score<=2) OR qa_source='rule_fallback'`，避免未质检 kp 污染打磨池。"未质检" ≠ "质检过且低分"。**横向边界（v2.3.0-part3.4 起）**：review_status 排除集合从 `('ignored','confirmed','merged')` 收紧为 `('ignored','merged')`。**允许 `confirmed`（已入库）条目进入候选池**。根因：全库 confirmed 化之后（当前库 2436 条 100% confirmed）旧 WHERE 把 1-2 分低分条目全部排除，维度⑤永久 100 分、自动跳过打磨，产品上"仪表盘显示 35 条低分 / 体检说 0 条"自相矛盾。已入库的低分条目才是最需要打磨后卖钱的目标。纵向 qa_score 边界不变
41. **F048 打磨不奖励"成功数"**：维度⑤得分公式 `max(0, 100 - 低分占比×100)`，不依赖本次打磨执行情况，避免"多生产低分去打磨"反激励
42. **`_safe_dim` 单维度异常隔离**：任一维度异常记 warn 事件降级，其他维度继续，整份报告不整体 failed
43. **白名单按 signature 精确匹配**：`dim_code|file:line|rule_id` 三段式；不按 `file:line` 模糊（未来新代码在老行号上引入真问题会被误过滤）
44. **issue 无限四态切换**：`pending↔intermittent↔fixed↔ignored` 任意方向，给老唐逃生口，支持 fixed/ignored 手动改回 pending
45. **V3 解析失败标 warn 不标 fail**：V3 本身不稳 ≠ 端点行为有问题，提示老唐人工复看避免误导
46. **前后端契约同步升级**：后端升级API返回结构时，前端所有消费点必须同步升级渲染逻辑。预防：改后端前grep前端消费点、列前端checklist、端到端手测。血的教训详见CHANGELOG

## 四、关键设计决策（"为什么这样做"锚点）

### F048 体检 / 打磨（v2.3.0-part2 锁定）

| 决策 | 选择 | 一句话理由 |
|------|------|-----------|
| 字段映射方案 | `_merge_ai_content` 固定 8 条映射，**不按 content_type 分流** | 方案 B 分流每加 content_type 都要改引擎；8 条收敛面更小 |

| /latest 瘦身返回 | 不含 full_report_json | 几百 KB 刷新卡片浪费带宽；详情走 /report/<rid> |
| 本地 splice 不重新请求 | 采纳/驳回/删除后本地 splice | 与后端 100% 无状态，误刷可重载 |
| 略过纯前端 | `healthReviewNext()` 只改指针不发请求 | DB 语义只有 apply/reject/manual，略过保留柔性决策空间 |

### F062 E2E 测试（v2.3.0-part3 锁定）

| 决策 | 选择 | 一句话理由 |
|------|------|-----------|
| 扫描范围 | 全量六维度（① 路由 / ② 启动 / ③ Prompt AST / ④ 字段 AST / ⑤ events V3 / ⑥ 代码异味 AST） | ③④⑥ AST 零成本；AI 花销只在 ② readiness + ⑤ 事件判断 |

| issue 跟踪 | 四态 + 偶发升级（7 天 > 5 次 → pending） | 避免报告疲劳；真正偶发浮到待修 |

| static_analyzer 误报处置 | 引擎层白名单二次过滤（按 signature） | 不反向放宽 AST 规则，保持"宁可多告警"检出力 |

### 仪表盘 / 质检补跑异步化 / 就绪度联动（v2.3.0-part3.2 锁定）

| 决策 | 选择 | 一句话理由 |
|------|------|-----------|
| 质检补跑任务槽 | 新建独立 `_qc_task` / `_qc_task_lock`，不进 `_task` 单例 | 质检补跑只写 `qa_score/qa_flags/qa_source/content_readiness` 窄面，与预处理/提取/体检/E2E 数据不冲突；允许并发 |
| 两次质检补跑本身 | 仍互斥（独立锁保证） | 没意义并发同种任务 |
| 前端进度面板 | 新建独立 `#qcTaskProgress` 与 `#taskProgress` DOM 并列 | 支持两者同时显示（真并发），用户可一屏看两个进度条 |
| 刷新恢复机制 | admin tab 切入时 `qcCheckRunningTask()` 轮询一次 | 对齐 F048/F062 已有 `checkRunningTask` 模式 |
| 就绪度联动规则 | `qa>=4 && draft → quotable`，**只升不降**，**不碰 premium** | editorial 轴（premium）与 qa 轴正交，混用会污染 premium 层；不降级给用户手动判断留余地 |
| 联动触发时机 | 质检补跑尾部自动触发 + 工具箱独立按钮手动触发 | 自动：省得用户记住"跑完还要再点一下"；独立按钮：不跑补跑时也能单独用 |
| 定位 | **v2.3.1 批量重算成熟度的保守前置版本** | 规则最小化（单条 draft→quotable），v2.3.1 再补齐 quotable→premium + 批处理 UI |
| qa_distribution 口径 | `qa_score IS NULL OR qa_score = 0.0` 归入 unscored | 与 `get_qc_rerun_summary` "待补跑=NULL 或 0.0" 对账一致；避免"未质检 0 vs 待补跑 2043"打架 |
| 标签卡 count=0 处理 | `get_tag_distribution` 只返 count>0 | 真实反映"多少标签在用"，不再用"定义了多少个标签"冒充 |
| 标签匹配字段 | `pattern = f'%"{tag_name}"%'` 非 tag_code | 存储侧 `_sanitize_tags` 存的就是 name，对齐立规则第 10 条 |
| SQLite 并发写兜底 | `PRAGMA busy_timeout=10000`，不做应用层 retry | WAL 已开 + DB 层等 10 秒，两层组合够用；应用层 retry 是双份保险增加复杂度 |

### 低分打磨候选池 / E2E issue 签名漂移（v2.3.0-part3.4 锁定）

| 决策 | 选择 | 一句话理由 |
|------|------|-----------|
| `get_polish_candidates` review_status 过滤 | 去掉 `confirmed` 排除，保留 `ignored`/`merged` 排除 | 全库 100% confirmed 化后，旧排除让维度⑤永久 100 分；已入库低分才是打磨 + 卖钱目标 |
| `qa_score>0` 纵向边界 | 保留不变 | 立规则第 40 条核心语义（未质检 ≠ 质检过且低分），本次只动横向 |
| `_write_issues` 签名 | 加 `report_id` 参数 | `upsert_e2e_issue` 真实签名 report_id 必填，旧调用漏传必错 |
| `upsert_e2e_issue` 调用契约 | `rule_id`/`detail` 合并进 `payload` 字典 | 对齐真实签名，旧 keyword 参数签名里不存在；数据不丢 |

### E2E 诊断包导出(v2.3.0-part3.5 锁定)

| 决策 | 选择 | 一句话理由 |


```
     ├── JSON 解析成功 AND recommendation ∈ {strong,optional,not} AND score∈[0,100]

     ├── client 视角规则:
```

**关键约束**:
- `score=50` 是中位数(不污染强推 Top 15% 排序,也不完全屏蔽于可选区)
- `recommendation` 三态与 AI 成功路径字面一致(`strong/optional/not`),前端无需区分两条路径的表达
- 规则兜底数**必回传汇总**,老唐在 modal 能看到"AI 成功 X 条 / 规则兜底 Y 条",信号清晰
- 降级链**不降级 AI 调用成本**(重试 1 次算 2 次调用,不是 1 次),老唐能看到真实花费

### F2 强推门槛(冻结档案 §6.4,前端实现)

AI 的 `recommendation` 字段**不是最终 level**,最终 level 由 api_server 按 composite_score 分位数决定:

```
composite_score = 权威×0.25 + 注解×0.25 + 质检×0.25 + 保鲜×0.25

权威分:official=100 / authoritative=75 / firsthand=50 / informal=25
注解分:has_annotation=True → 100,False → 0
质检分:qa_score × 20
保鲜分:fresh=100 / warning=50 / expired=25 / NULL=75(未体检给中位值)

按 composite_score 降序排,Top 15% → level='strong',中段 40% → level='optional',
尾部 45% → level='low'(不返回前端)
```

前端两档 tab(强推 / 可选)按 `level` 过滤,AI `recommendation` 仅作为行级展示("AI 理由: xxx")。

## 十二、设计思想（架构级原则，最后的防失忆锚点）

1. **代码质量失败让解释器崩**：不静默降级，让问题立刻暴露
2. **数据契约不兑现肉眼可见**：维度分异常（0 或 100）不假绿
3. **单条 AI 偶发失败维度隔离**：`_safe_dim` 包装，不整份报告 fail
4. **事件日志是事实源**：F062 维度⑤权重高于 response 表面成功
5. **白名单精确到 signature 不模糊到行号**：避免未来新代码在老行号上引入真问题被误过滤
6. **跨对话开发三次对齐**：alpha 契约→骨架 / beta 代码→锚点 / 正式版 端到端→metrics
7. **schema 单一来源 + 启动兜底 init_tables**：`init_tables()` 是唯一真相，api_server 启动时 silent 重入追齐老库（v2.3.0-part3.1 起铁律）
8. **对外 import 契约模块级包装**：首次交付即提供，避免只定义类方法
9. **接口先定契约再写代码**：对话 1 基础层立 Prompt + DB 契约，对话 2 引擎层消费契约，对话 3 界面层接引擎
10. **跨版本调用必对照真实签名**：不相信记忆不相信旧文档,必 grep 源码,是 v2.3.0-part3.1 血泪立规则
11. **存储/查询口径一致性**：针对 JSON 字段的 SQL 查询前必 grep 写入点确认格式（name/code/中/英/扁平/嵌套），旧版"count=0 也塞入掩盖 bug"是反面教材。v2.3.0-part3.2 血泪立规则
12. **给老唐逃生口**：无限四态切换 / 略过按钮纯前端 / 本地 splice 可误刷重载 / 破例加方法要有书面理由
13. **可观测性 > 看起来更快**：质检补跑曾"响应是快了（同步阻塞但跑完即返）"但不可观测、不可并发、刷新即失；part3.2 改异步后"响应更慢了（立即 202 然后轮询）"但全流程可观测，是更优工程设计。未来新长任务都按此模式
14. **一项修复可能暴露更下层的 bug**：part3.2 的 `count>0` 过滤看似只是"UI 不显示空行"，实际暴露了潜伏 3 个月的 tag_code vs tag_name 查询错误。遇到这种"修 A 结果出现 B"的连锁，**不要回滚 A**，要向下挖 B 直到触到真正的底。这也是第 11 条的推论
15. **前后端是两条腿，契约变动时必须一起迈**：后端改 API 返回结构时前端消费点必须同步改；改一端不改另一端就是"交付一半"。审核统计 JSON 裸喷 UI 潜伏 2 个月是反面教材。v2.3.0-part3.3 立规则第 46 条的思想基础
16. **"看起来完成" vs "用户能用"**：part3.3 的保鲜 loading / 体检无低分提示 / E2E 耗时 `<1s` 这三件事都属于"功能跑正常但用户看不明白"的 UX 顽疾。后端返回 200、数据也对，但用户不知道发生了什么或怎么理解 — 这不叫完成，叫"技术完成工程师满意，业务验收客户困惑"。每次交付末尾自问一句："如果我第一次见这个功能，我能 30 秒内看懂它说什么吗？"
17. **筛选条件的边界要跟业务现状对齐**：`get_polish_candidates` 排除 `confirmed` 条目在 v2.3.0-part2（F048 上线）是合理的——那时审核流程是"打磨完才入库"。但 part3.2 上线就绪度联动后，qa≥4 自动升 quotable = confirmed，全库最终都会 confirmed 化，旧排除条件就把所有低分条目一并过滤掉了。**业务流程变化时，查询过滤条件必须回头校对一次**。交付 checklist：(1) 列出所有新旧业务状态；(2) 列出每个状态是否应进候选池；(3) WHERE 子句按实际业务意图写，不沿用旧直觉。v2.3.0-part3.4 血泪立规则
18. **文档是"让下次开发不失忆",不是"再写一遍代码"**:代码是真相,文档是向导。向导不复制地图的每一条街道,而是告诉访客"这条街当年塌过桥"(踩坑)、"本地人走这边近"(契约)、"那边是死胡同"(退役组件)。立规则第 47 条管"精简到什么边界",第 48 条管"精简的方向指针",设计思想第 18 条是元精神。老唐每次修改都上传最新代码给 Claude → 文档里**禁止**重复代码一眼可见的内容(签名 / SQL / 常量表 / 目录树);文档只保留代码里**读不出**的(立规则 / 踩坑 / 契约 / 为什么)。v2.3.0-part3.5 血泪立规则

19. **交付不是 outputs,是 present_files**(v2.3.2,立规则 50 流程末端的元应用):每轮 Phase 3 代码完成后,**必须** present_files 给老唐才算交付完毕。outputs 是中间产物,Claude 看得到但老唐看不到 / 下载不到。漏 present_files = 没交付。**血的教训**:v2.3.2 Phase 3 part3b 完成后 Claude 直接跳过 present_files 跑去做 part4,老唐发现并指正"review.html 和 f056_viewer.html 你都还没交付给我,怎么能开始下一步?"。**与立规则 50 关系**:立规则 50 是"7 项验证清单"(2026-04-28 起,老版 6 项),present_files 是清单跑完后的流程末端动作,容易被当成"自然流程末端的可省略仪式"。设计思想第 19 条把它升格为"交付定义本身":**没 present_files 就不存在交付,Phase 4 操作清单都是空话**

20. **对话内闭环不是规则,是工程纪律**(v2.3.2 立规则 53 真精神升级):立规则 53 字面是"Phase 3 必须对话内闭环",但真精神是"**别凭感觉喊配额超时**"。v2.3.2 Phase 3 part1/part2/part3a 三轮 Claude 都凭感觉喊"配额不够要新对话",老唐三次"继续"督促才完成。每次都是误判 —— 实际配额都充足,只是恐惧驱动的自我设限。**判别法则**:如果"差点收尾"和"完整交付"之间只差 5-8 次工具调用,**继续干**;如果差距 ≥30 次工具调用,**主动评估拆 a/b 并透明告知**(立规则 57)。**最差的情况是凭感觉中断**:既不评估也不拆,只是缩手 —— 这就是违规

## 十三、Claude 自我强制机制(TASK-RADAR · 违规防护墙)

立规则 58 的执行支撑层(2026-04-28 起)。立规则立了不等于被执行 —— 立规则 9 应验 13 次,立规则 53 自证 4 次。本章把"立规则被执行"从"自觉"升级为"机制"。

### 13.1 任务启动雷达清单(强制输出格式)

每次 Phase 3 开工前 Claude **必先**输出如下结构(老唐肉眼可核查):

```
【本次任务规则雷达扫描清单】
- 任务类型: [代码改动 / 文档改动 / 立新规则 / 数据迁移 / 其他]
- 触发立规则: [grep 后识别的编号列表]
- 对应执行动作:
  · 立规则 X → 具体动作
  · ...
- 承诺不跳过: [关键验证项编号]
```

**未输出此清单不能进入下一步代码/文档动作**。

### 13.2 关键规则快捷码(双方沟通效率)

| 快捷码 | 立规则 | 含义 |
|-------|-------|------|
| **GREP-SIG** | 9 | 调外部方法前 grep 真实签名 |
| **CP-PATCH** | 49 | 大文件拷贝+精准替换 |
| **VERIFY-7** | 50 | 7 项验证(含冗余清理) |
| **DOC-CUT** | 51 | 项目文件做减法 + 立规则盘存 |
| **TASK-RADAR** | 58 | 任务启动规则雷达 |

### 13.3 老唐反作弊触发器(随时打断)

| 老唐喊话 | Claude 必须立刻做的动作 |
|---------|----------------------|
| "9?" / "GREP-SIG?" | 立刻停止当前动作,回答"我 grep 了 XXX 真实签名,结果 YYY"或"我没 grep,现在补" |
| "7?" / "VERIFY-7?" | 立刻输出 7 项验证清单逐条勾选 |
| "盘点?" / "DOC-CUT?" | 立刻执行立规则盘存,grep 现有规则清单 |
| "雷达?" / "TASK-RADAR?" | 立刻输出"本次任务规则雷达扫描"清单 |

Claude **必须立刻停下当前动作先回答**,不能"等会儿"。

### 13.4 自检失败暴露原则

Claude 跳过任何强制验证步骤,**必须主动暴露**:

- "立规则 X 的第 Y 项我跳过了,理由 Z"
- 不能装作没看见
- **暴露是规则迭代的真实养料**(没有暴露 = 立规则 9 还要应验第 14 次)

### 13.5 失效信号(老唐警觉)

下列信号出现 = 13.1~13.4 失效 → 必须新开对话强化机制:

- Claude 直接进入代码动作未输出雷达清单
- 老唐喊快捷码 Claude 没立刻停下回答
- 同一类老错误在 14 次以上应验
- Claude 跳验证后没主动暴露,老唐通过事后核查发现

### 13.6 LLM 本质局限的诚实承认(老唐设问 2026-04-28)

为什么 77 条规则反复犯老错?Claude 自检 5 条本质局限:

1. **模式匹配优先于事实查证**:训练目标使然,看到方法名按记忆生成参数
2. **意识层 vs 反射层割裂**:读规则在意识层,写代码在反射层,标语压不过肌肉记忆
3. **长上下文衰减**:对话越长,开头读过的规则越褪色
4. **规则缺少自动触发**:规则是"应该做"不是"被强制做",触发时机模糊
5. **配额焦虑/工程师心理**:"赶紧搞完"压过"做对"

**结论**:再立 100 条限速规则不如装 1 个测速摄像头。立规则 58 + §十三 就是测速摄像头本身。
