# 乡村振兴知识库搭建助手 — 迭代升级操作手册

> 版本：v1.0.0 | 适用对象：系统使用者（零编程基础）
> 本手册面向持续改进，当你需要修改、升级、回滚系统时使用

---

## 第一章：为什么需要版本管理

### 1.1 大白话解释

想象你在装修房子：

- **修复版本**（v1.0.0 → v1.0.1）：相当于补了个漏水的水龙头，房子结构没变
- **功能版本**（v1.0.0 → v1.1.0）：相当于加装了一间储物室，房子更好用了
- **主版本**（v1.0.0 → v2.0.0）：相当于推倒重建了一面墙，格局变了

每次装修前你都会拍照记录"改之前什么样"，这就是版本管理。万一新装的不满意，对着照片恢复就行。

### 1.2 版本号规则

```
v1.0.0
 │ │ │
 │ │ └── 修复版本：Bug修复、Prompt微调、界面小优化
 │ └──── 功能版本：新增完整模块（如搜索、去重、同步）
 └────── 主版本：架构重大变更、数据库结构重构
```

### 1.3 为什么不能跳过版本管理

- 没有版本记录 → 出问题不知道是哪次修改导致的 → 无法回退
- 有版本记录 → 精确定位问题 → 一键回退到上个正常版本

## 第二章：升级需求描述模板

### 2.1 模板完整内容

每次你发现需要改进的地方，填写以下模板发给 Claude：

```
【升级需求描述】

当前系统版本：v____
发现问题的场景：（我在做什么操作时发现的）
问题描述：（我看到了什么现象，期望看到什么）
问题类型：
  □ 功能不符合预期
  □ 缺少某个功能
  □ Prompt需要调整
  □ 界面/操作体验问题
  □ 报错/系统崩溃
  □ 其他：____
涉及的操作步骤：（我是按什么顺序操作的）
期望的改进效果：（改完后我希望看到什么结果）
优先级：高 / 中 / 低
附加说明：
```

### 2.2 填写示例

**示例一：Prompt调整类**

```
【升级需求描述】

当前系统版本：v1.0.0
发现问题的场景：处理了5份增减挂钩政策文件后审核知识点时
问题描述：AI提取政策文件时，"关键时间节点"这个字段经常漏掉，
  比如"2025年12月31日前完成验收"这种信息没有被提取出来。
  期望这类时间节点能被完整提取。
问题类型：
  ☑ Prompt需要调整
涉及的操作步骤：
  1. 把5份PDF放入 data/pending/
  2. 双击"处理新文件.bat"
  3. 双击"启动审核界面.bat"
  4. 查看提取结果，发现时间节点缺失
期望的改进效果：政策文件中出现的所有截止日期、生效日期、
  阶段节点都能被提取到"关键时间节点"字段中
优先级：中
附加说明：这5份文件都是四川省级文件，文号格式是"川自然资规〔2025〕X号"
```

**示例二：新增功能类**

```
【升级需求描述】

当前系统版本：v1.0.0
发现问题的场景：审核了200多条知识点后想导出一份清单给客户看
问题描述：审核界面没有导出功能，我没办法把已确认的知识点
  导出为Excel或PDF给别人看。
问题类型：
  ☑ 缺少某个功能
涉及的操作步骤：无（因为功能不存在）
期望的改进效果：审核界面增加一个"导出"按钮，可以按分类导出
  已确认的知识点为Excel文件
优先级：中
附加说明：导出的Excel最好包含：标题、分类、标签、核心内容、原文路径
```

### 2.3 填写注意事项

- **场景要具体**：不要写"提取不好"，要写"处理XX类文件时，XX字段经常漏掉"
- **贴报错信息**：如果是报错，把黑色窗口中的错误信息截图或复制文字发给Claude
- **一次一个需求**：不要在一个模板里塞多个不同的需求，每个需求单独填写
- **优先级诚实填**：高=影响正常使用，中=不影响使用但体验不好，低=锦上添花

## 第三章：Claude辅助迭代标准工作流

每次迭代严格按以下5个阶段推进，每个阶段有明确的交接标准。

### Phase 1：需求提交

**你需要做什么**：
1. 填写升级需求描述模板
2. 在 Claude 对话中发送给 Claude
3. 如有报错截图或示例文件，一并附上

**Claude 会给你什么**：
"影响范围评估"报告，包含：
- 需要修改哪些文件（列出文件名和路径）
- 是否涉及数据库结构变更
- 复杂度评估（简单/中等/复杂）
- 预计改动量
- 是否有风险需要特别注意

**如何判断这个Phase完成了**：
你看到了 Claude 的影响范围评估，并且理解了改动的大致范围。

---

### Phase 2：方案确认

**你需要做什么**：
1. 阅读 Claude 的影响评估
2. 如有疑问，继续追问
3. 确认无误后回复"继续"或"方案确认，请开始"

**Claude 会给你什么**：
修改逻辑说明（用大白话，不是代码），包括：
- 打算怎么改（思路）
- 改完后效果是什么
- 有没有多种实现方式供你选择

**如何判断这个Phase完成了**：
你明白了 Claude 打算怎么改，并且同意这个方案。你回复了明确的确认信号。

---

### Phase 3：代码交付

**你需要做什么**：
1. 接收 Claude 输出的文件
2. 每个文件都有完整代码和保存路径
3. 暂时不要替换文件，先进入 Phase 4

**Claude 会给你什么**：
- 每个受影响文件的**完整新版本代码**（不是片段，是整个文件）
- 每个文件的**保存路径**
- 如有数据库变更：**迁移脚本**（一个单独的 .py 文件）
- **新版本号建议**（比如 v1.0.0 → v1.0.1）
- **CHANGELOG 条目**（记录本次变更内容）

**如何判断这个Phase完成了**：
你收到了所有需要替换的文件，并且 Claude 明确说"代码交付完成"。

---

### Phase 4：安全升级

**你需要做什么**：

**Step 1 — 备份（⚠️ 最重要的一步！）**

1. 复制 `knowledge_base.db` 到安全位置
2. 复制即将被替换的旧文件到安全位置
3. 记录当前版本号

**Step 2 — 替换文件**

1. 根据 Claude 给出的路径，找到每个需要替换的文件
2. 用新版本文件替换旧文件
3. ⚠️ 以下文件绝对不要随意替换（除非 Claude 明确要求）：
   - `config/settings.json`（你的配置信息）
   - `config/encryption.key`（你的加密密钥）
   - `knowledge_base.db`（你的知识库数据）

**Step 3 — 运行迁移脚本（如需要）**

如果 Claude 提供了数据库迁移脚本：
1. 把迁移脚本保存到 scripts/ 目录
2. 双击 Claude 指定的 .bat 文件运行迁移
3. 等待窗口显示"迁移完成"

**Step 4 — 验证升级成功**

1. 双击 `bat/检查系统状态.bat` — 8项全部通过
2. 双击 `bat/启动审核界面.bat` — 界面正常打开
3. 检查已有的知识点是否还在 — 数据没有丢失
4. 如果有新功能，测试新功能是否正常

**Step 5 — 推送到 GitHub**

1. 打开 GitHub Desktop
2. 查看左侧修改的文件列表，确认只有你替换的文件
3. Summary 填写：版本号 + 简要说明（比如 `v1.0.1 修复审核界面分页bug`）
4. 点击 Commit to main → Push origin

**Step 6 — 更新 Claude Projects 项目文件**

1. 打开 Claude Projects
2. 更新受影响的项目文件（Claude 会告诉你哪些项目文件需要更新，并提供新内容）
3. 主要更新：01_代码库快照.md、02_CHANGELOG.md

**如何判断这个Phase完成了**：
系统检查通过、审核界面正常、数据完整、GitHub已推送、项目文件已更新。

---

### Phase 5：回滚预案

如果升级后出现问题，参见本手册第五章的回滚操作手册。

```
Phase 2  你：确认方案          Claude：修改逻辑说明     完成标志：你回复"继续"

```

## 第四章：升级操作实操手册

### 4.1 升级前必做清单

每次升级前，逐项打勾确认：

```
□ 记录当前版本号：v______
□ 已备份 knowledge_base.db 到安全位置
□ 已备份即将被替换的旧文件
□ 已关闭审核界面（如果在运行中）
□ 已关闭所有正在运行的.bat窗口
□ Claude 已明确交付完所有文件
```

### 4.2 文件替换操作

**如何找到需要替换的文件**：

Claude 会给出明确路径，比如 `scripts/extractor.py`。你需要：
1. 打开项目根目录（比如 `D:\GitHub\rural-revitalization-kb`）
2. 按路径层级打开文件夹：先打开 `scripts/`，找到 `extractor.py`
3. 用新文件替换旧文件

**如何安全替换**：

1. 先把旧文件改名，在文件名后加 `_旧`（比如 `extractor_旧.py`）
2. 把新文件放入同一目录
3. 确认新文件名正确（没有多余的后缀）
4. 验证无误后再删除旧文件

**⚠️ 绝对不能随意替换的文件**：

| 文件 | 原因 | 什么时候才能替换 |
|------|------|-----------------|
| config/settings.json | 包含你的加密API Key | 仅当Claude明确要求修改配置格式时 |
| config/encryption.key | 加密密钥，丢了API Key就解不开了 | 永远不要替换，除非重新配置 |
| knowledge_base.db | 你全部的知识库数据 | 仅当Claude提供迁移脚本时配合操作 |

### 4.3 数据库迁移操作

**如何判断是否需要迁移**：

Claude 会在 Phase 3 代码交付时明确告知：
- "本次升级**不涉及**数据库变更" → 不需要迁移
- "本次升级**涉及**数据库变更，请运行迁移脚本" → 需要迁移

**如何运行迁移脚本**：

1. Claude 会提供一个迁移脚本文件（比如 `migrate_v100_to_v101.py`）
2. 把它保存到 scripts/ 目录
3. Claude 会告诉你如何运行（通常是双击一个配套的 .bat 文件）
4. 运行后窗口会显示迁移进度和结果

**如何验证数据完整性**：

迁移完成后：
1. 双击 `bat/启动审核界面.bat`
2. 查看统计数字：已确认的知识点数量应该和升级前一致
3. 随机打开几条知识点，确认内容没有变化
4. 如果数据有异常，立即回滚（参见第五章）

### 4.4 升级验证完整清单

```
□ 检查系统状态.bat — 8项全部通过
□ 启动审核界面.bat — 界面正常打开
□ 已确认知识点数量 — 与升级前一致
□ 随机查看3-5条知识点 — 内容完整无损
□ 新功能测试 — 按Claude说明测试新功能
□ 处理新文件测试 — 放一个测试文件跑一遍全流程（可选但推荐）
```

## 第五章：回滚操作手册

### 5.1 什么情况下需要回滚

- 升级后系统检查不通过
- 审核界面打不开或显示异常
- 知识点数据丢失或内容变化
- 处理新文件时持续报错（而升级前正常）
- 你自己觉得不对劲，说不清哪里有问题

**原则**：宁可回滚再排查，不要在异常状态下继续使用。你的数据安全是第一位的。

### 5.2 回滚的完整操作步骤

不要紧张，回滚就是"把旧文件换回来"，你的数据不会丢。

**Step 1**：停止所有正在运行的服务

1. 关闭浏览器中的审核界面
2. 关闭所有黑色命令行窗口
3. 确认没有 .bat 文件在运行中

**Step 2**：恢复旧版本代码文件

方式A — 从本地备份恢复（如果你在升级前做了备份）：
1. 找到升级前备份的旧文件
2. 用旧文件替换回当前的新文件

方式B — 从 GitHub 恢复（如果你在升级前推送过旧版本）：
1. 打开 GitHub Desktop
2. 点击 History 标签
3. 找到升级前的最后一次提交
4. 右键点击 → Revert this commit
5. 点击 Push origin 推送

**Step 3**：恢复数据库（如果做了数据库迁移）

1. 用备份的 `knowledge_base.db` 替换当前的数据库文件
2. ⚠️ 这会丢失迁移后新增的数据，但能保证旧数据完整

**Step 4**：验证回滚成功

1. 双击 `bat/检查系统状态.bat` — 8项通过
2. 双击 `bat/启动审核界面.bat` — 正常打开
3. 检查知识点数量和内容 — 恢复到升级前的状态

**Step 5**：告知Claude继续排查

在对话中告诉Claude：

```
升级到 v____ 后出现问题，已回滚到 v____。
问题现象是：____
请帮我排查原因。
```

Claude 会分析原因并提供修正后的升级方案。

### 5.3 回滚后的心态

回滚不是失败，而是正常的软件开发流程。专业的软件团队每天都在做回滚。回滚说明版本管理体系在正常工作——你有"后悔药"可以吃，这正是我们建立版本管理的意义。

## 第六章：CHANGELOG 维护指南

### 6.1 什么是 CHANGELOG

CHANGELOG.md 是一个"装修日志"，记录每次升级改了什么。它存放在项目根目录下。

### 6.2 格式规范

每次升级后，在文件顶部新增一条记录（最新的永远在最上面）：

```markdown
## v1.0.1 -- 修复审核界面分页Bug

发布日期：2026-03-25

变更内容：
- 修复：审核界面翻页后筛选条件丢失的问题
- 修复：批量确认时最后一条未被正确处理

受影响文件：scripts/api_server.py, web/templates/review.html
数据库迁移：不需要
```

### 6.3 你需要做什么

通常 Claude 会在 Phase 3 代码交付时直接给出 CHANGELOG 条目的内容。你只需要：

1. 打开项目根目录的 `CHANGELOG.md`
2. 把 Claude 给的内容粘贴到文件**最顶部**（在旧记录之前）
3. 保存文件

如果你想自己记录一些补充信息（比如"这次升级是因为处理四川某某项目文件时发现的问题"），直接加在变更内容后面即可。

## 第七章：典型迭代案例示范

### 案例一：Prompt调整类（简单迭代）

**背景**：处理政策文件时，发现AI总是漏掉"适用范围"信息。

**Phase 1 — 需求提交**

你发给Claude：
```
当前系统版本：v1.0.0
发现问题的场景：处理了3份全域土地综合整治政策文件后审核
问题描述：AI提取结果中没有"适用范围"信息，比如"本办法适用于
  成都市范围内"这种信息被忽略了
问题类型：Prompt需要调整
期望：政策文件的提取结果中增加"适用范围"字段
优先级：中
```

**Phase 2 — Claude的影响评估**

Claude回复：
```
影响范围评估：
- 需要修改的文件：scripts/prompts/prompt_templates.py（1个文件）
- 数据库变更：不需要
- 复杂度：简单
- 改动内容：在 POLICY_EXTRACT_PROMPT 中增加"适用范围"的提取要求
```

你回复："继续"

**Phase 3 — 代码交付**

Claude给出 prompt_templates.py 的完整新版本代码，并说明：
- 版本号建议：v1.0.1
- CHANGELOG条目内容

**Phase 4 — 安全升级**

1. 备份旧的 prompt_templates.py
2. 替换为新文件
3. 放一个测试政策文件跑一遍，检查是否提取出了"适用范围"
4. 确认OK后推送到GitHub
5. 更新Claude Projects中的05_Prompt模板库.md

**总耗时**：约15分钟

### 案例二：新增功能类（中等迭代）

**背景**：你希望在审核界面中增加一个"导出Excel"功能。

**Phase 1 — 需求提交**

你发给Claude：
```
当前系统版本：v1.0.1
发现问题的场景：审核了300条知识点后想给客户看一份清单
问题描述：审核界面没有导出功能
问题类型：缺少某个功能
期望：增加"导出"按钮，可以按分类导出已确认知识点为Excel
优先级：中
```

**Phase 2 — Claude的影响评估**

Claude回复：
```
影响范围评估：
- 需要修改的文件：
  1. scripts/api_server.py（新增导出API接口）
  2. web/templates/review.html（前端增加导出按钮）
  3. requirements.txt（可能需要新增 openpyxl 依赖）
- 数据库变更：不需要
- 复杂度：中等
- 风险提示：需要确认 openpyxl 是否已安装
```

你回复："方案确认，请开始"

**Phase 3 — 代码交付**

Claude给出3个文件的完整新版本，以及：
- 版本号建议：v1.1.0（新增完整功能，功能版本号升级）
- CHANGELOG条目
- 可能需要运行一次 `bat/安装依赖库.bat`

**Phase 4 — 安全升级**

1. 备份旧文件
2. 运行 `bat/安装依赖库.bat`（安装新依赖）
3. 替换3个文件
4. 启动审核界面，测试导出按钮
5. 推送GitHub + 更新Projects项目文件

**总耗时**：约30分钟
